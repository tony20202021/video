# ML-пайплайн: классификация и идентификация

## Модели

Все модели в формате **ONNX** — единый рантайм, не требует PyTorch/TF в production.

| Задача | Модель | Размер | Скорость на CPU | Статус |
|--------|--------|--------|-----------------|--------|
| Детекция людей | YOLOv8n | ~13 MB | ~20–40 мс/кадр | **Готово** `.models/detect/yolov8n.onnx` |
| Классификация группы (Модель 1) | MobileNetV3-Small | ~6 MB | ~5–10 мс/crop | **Активна** `.models/classify/v3_1.onnx` (датасет v3, 10 015 файлов) |
| Идентификация жителя (Модель 2) | MobileNetV3-Small | ~10 MB | ~5–10 мс/crop | Нужно обучить |

## Multi-label Модели 1 (датасет v4)

**Проблема single-label.** YOLO кропает человека с паддингом 0.40 — в кроп часто попадает
несколько людей РАЗНЫХ классов (житель + курьер и т.п.), но метка одна (softmax + argmax).
Модель учится на «шумной» метке и теряет со-встречающиеся классы.

**Решение (multi-label, начиная с датасета v4).** Кроп остаётся per-person (bbox YOLO),
но размечается и предсказывается **НАБОРОМ классов**: sigmoid + порог на каждый класс
(вместо softmax + argmax). Меняется только Модель 1 (группы); Модель 2 (жители) не меняется,
но получает вход уже из новой Модели 1.

**Формат меток** (`src/common/utils/multilabel.py`, `labels.json`):

```
v2 (multi): {"version": 2, "task": "...", "labels": {img: ["class1", "class2"]}}
v1 (old):   {"version": 1, "labels": {img: "class"}}      ← читается как {img: ["class"]}
```

Пустой список `[]` = размечено «ни одного класса»; отсутствие ключа = ещё не размечено.
`multilabel.load_labels()` читает оба формата (подхват старой разметки), `save_labels()`
пишет v2. `classes_from_probs(prob_map, thresholds)` → набор классов ≥ порога.

**Структура датасета v4** (каталоги — для просмотра глазами; ИСТИНА = `labels.json`):

```
.data/groups/v4/dataset/
  single/<class>/img.jpg   — кропы с ОДНИМ классом (по подкаталогам)
  multi/img.jpg            — кропы с НЕСКОЛЬКИМИ классами (плоско)
  labels.json              — ОБЩИЙ, {img: [classes]} (пути относительно каталога датасета)
  sources.csv              — аудит
```

Старые v1/v2/v3 — single-label, НЕ мигрируются (в них лежит маркер `_FORMAT_single-label.txt`).

**Обучение** (`3_train_groups.py`): `BCEWithLogitsLoss` по мультихот-таргетам, `pos_weight`
= neg/pos на класс (баланс), стратификация по КОМБИНАЦИИ классов. Метрики: per-class
precision/recall/F1/AP + macro/micro-F1 + mAP + subset-accuracy. Порог на КАЖДЫЙ класс
подбирается по F1 на валидации → в манифест. Старые single-label датасеты тоже читаются
(1 класс → 1-hot). Читает и v4 (`single/`+`multi/`+`labels.json`), и папки-классы, и `labels.json`.

**Инференс модель-зависимый** (`src/ml/classify.py`): манифест модели (`<tag>.json`) хранит
`multi_label` + `thresholds`. Если `multi_label=true` → sigmoid + пороги на класс →
`predict_classes()` возвращает НАБОР; иначе (старые модели) softmax + argmax как раньше.
Логиты старой модели обучены под single-label, поэтому sigmoid на них смысла не имеет —
реальный multi-label только после переобучения (BCE).

**Пайплайн** (`3_classify_groups.py`) раскладывает кроп по числа предсказанных классов:
`single/<class>/` (1), `multi/` (≥2), `uncertain/` (0), `unknown/` (модель не загружена);
ведёт общий `labels.json` (v2) и `classifications.csv` (+ колонки `classes`, `n_classes`,
`to_identify`). В `identify` (Модель 2) идут кропы, чей набор содержит `1_resident`/`4_guest`:
`single/1_resident/`, `single/4_guest/` и `multi/` (отфильтрованные по `labels.json`).

**Псевдо-метки** (`skip`/`unknown`/`uncertain`/`new` — `EXTRA_DATASET_DIRS`) взаимоисключающи
с настоящими классами: выбрал хоть один класс → псевдо-метки снимаются автоматически
(`_clean_label_set`). `uncertain` — «нет уверенного класса» (низкая conf инференса), `skip` —
отложено (битый кроп). Кропы с псевдо-меткой **исключаются из обучения** (`3_train_groups`).

**Разметчик** (`2_label_ui.py`) — мультивыбор во всех 3 режимах:
- режим разметки: классы тогглами ☑/☐ (клавиши 1-N), `Space/Enter` — вперёд, `U` — пропустить (skip);
- галереи сессии и датасета: плитки сгруппированы по КОМБИНАЦИИ классов; батч по выделению —
  **трёхпозиционные чек-боксы** (☑ у всех выбранных · ☐ ни у кого · ◪ N/M частично; клик: у всех
  включён → снять у всех, иначе → включить всем) + «Пропустить» (skip) + «Очистить»; модалка
  одиночного просмотра — те же тогглы/Пропустить/Очистить.
Подхватывает старую single-метку как 1-элементную; смешанные наборы `класс+uncertain` чистятся
при загрузке. В каталоге датасета правка набора перекладывает файл `single`↔`multi`↔`skip`.

**Сборка датасета v4** (`scripts/train/build_groups_v4.py`): v4 = v3-датасет (курированный, уже
включает v1+v2) + v3-инференс (новое, 0 пересечений). Раскладка `single/<class>/` + `multi/` +
`labels.json`(v2) + `sources.csv` + `dataset.json`. Доминирующий `1_resident` **прореживается** до
баланса с минорами: окно 30 сек по (камера, дата), K кропов на бакет, отбор — **farthest-point
по pixel-diff** (`_diff` — K максимально разных по картинке кадров на визит, а не одинаковые
стоячие). Миноры/мульти — целиком; skip/uncertain исключены. Пример: v3-датасет 10015 +
v3-инференс 9429 → **v4 ~7253** (1_resident 3916 ≈2× guest 1800, delivery 613, utilities 1017; мульти 93).

**Поток v4:** разметить инференс в `2_label_ui` → `build_groups_v4.py` → обучить
(`3_train_groups --data .data/groups/v4/dataset --weighted-sampling`) → сравнить метрики с
предыдущими версиями → активировать `v4_1` + `GROUPS_VER=v4` + рестарт сервисов.
(Старые `dataset_groups.py` build/apply и `dataset_v2_from_inference.py` — single-label, на
v2-метках выводят подсказку и не запускаются; миграция отложена.)

## Темпоральное сглаживание классов (шаг 3b, между classify и identify)

**Проблема.** Классификатор ошибается на ЕДИНИЧНЫХ кадрах: в потоке из многих правильно
определённых резидентов иногда 1-2 кадра размечены как гость/доставка. Интуиция: в
последовательности одного человека класс меняется редко → единичные ошибки можно убрать.

**Метод — активный режим: классическое бегущее окно вероятностей** (`src/common/utils/temporal_smooth.py`,
скрипт `scripts/pipeline/3b_smooth_groups.py`). Включается `SMOOTH_PROB_WINDOW>0` (в проде `=3`):
1. по `classifications.csv` строим последовательности **(камера, время, вероятности p_<class>)**
   по **ВСЕМ** кадрам — M>1 (`pNofM`), `multi`, `uncertain`, `unknown` тоже (у них есть probs);
2. **сегментация на визиты** по паузам во времени (пауза > `gap` → новый визит; дефолт **5с**);
3. **классическое бегущее окно ВНУТРИ визита** (`window_average`): вероятности КАЖДОГО кадра
   заменяются на среднее соседей в окне вокруг него → берётся `argmax`. Окно: **±`SMOOTH_PROB_WINDOW`/2 сек**
   (полный размер `=3с` → **±1.5с**) И не более **`SMOOTH_PROB_WINDOW_K`** кадров
   (`=7` → **±3 кадра**), берётся пересечение; на краях визита окно одностороннее. Меняется только
   значение самого кадра (центра), соседи — как есть;
4. **`images/` НЕ мутируется** (неизменяемый выход Модели 1). Результат пишется в сайдкар
   `inference/smoothed/<date>/` — **самодостаточно для разметки и downstream**:
   - `classifications_smoothed.csv` — `crop, cam, model_class, smoothed_class, changed, rel, p_<class>…`
     (`smoothed_class` в **col4** — identify читает `$4`; `rel` = путь кропа относительно `images/<date>`;
     `p_<class>` = probs модели → CSV годится как `--probs-csv` для разметчика). **ЕДИНСТВЕННЫЙ авторитетный
     машинный выход сглаживания** — сглаживатель пере-генерит его свободно;
   - **`labels.json` сглаживатель НЕ пишет.** Это файл РУЧНОЙ разметки: его создаёт/ведёт ТОЛЬКО человек
     в `2_label_ui` (при первом сохранении). Наличие = «дату проверил человек», отсутствие = «берём авто».
     Разметчик, когда `labels.json` нет, **сидит стартовые метки из `smoothed_class`** (CSV). Поэтому
     любой пересчёт CSV (смена параметров/версии/рост CSV) **не затирает ручную разметку**;
   - кропы НЕ перекладываются, `images/labels.json` НЕ переписывается.

**Резервный режим — HMM/Viterbi** (при `SMOOTH_PROB_WINDOW=0`): сегментация на визиты + Viterbi
внутри визита (переходы `p_stay`, эмиссия = probs модели) + опциональный **гейтинг** (max prob ≥ `gate`
не трогаем) + три предохранителя (guard/min-minority/veto, по умолчанию выкл). В бегущем окне
Viterbi/gate/предохранители НЕ применяются.

**Все кадры, включая M>1.** По `.plan` сглаживаются ВСЕ кадры без исключений: и многолюдные
(`pNofM`, M>1 — участвуют в бегущем окне и сами исправляются), и `multi`/`uncertain`/`unknown`.
Раньше M>1 держались лишь как контекст (боязнь смешать разных людей у двери) — теперь тоже
сглаживаются. Полноценно проблему смешивания решит трекинг по персонам (пока не сделан).

**Калибровка — минимальная длительность РЕАЛЬНОГО прохода (подтверждено на кейсах).** Реальный
человек может быть в кадре очень коротко. Подтверждённый кейс `cam_01_9_d 20260713 19:19:45–47`:
весь визит **~2с** (гость стоит у двери всё время, 34 кадра), а со-встречный **резидент** только
**открыл дверь — ~0.4с** (4 кадра M=2 в пределах одной секунды). **Вывод для алгоритмов сглаживания:**
любой фильтр «минимальной длины сегмента» (если добавлять к Viterbi/окну против пограничных бликов)
должен быть **< ~0.5с**, иначе затрёт реальные короткие проходы (резидент, мелькнувший у двери).
Текущие `gap=5с` и окно `±3с` такие проходы НЕ режут. Копить подобные кейсы (минимальные проходы
живых людей) — здесь.

### Параметры (зафиксировано)

**Активный алгоритм — Viterbi/HMM БЕЗ гейта** (замер на истине: **16.9%** ошибок против 21.3% у окна).
Все кадры. Прод-конфиг в `.env`:

| Параметр | env | Значение | Смысл |
|----------|-----|----------|-------|
| Липкость (Viterbi) | `SMOOTH_P_STAY` | **0.9** | **АКТИВНЫЙ метод — Viterbi.** Вероятность сохранить класс между кадрами (выше → меньше флипов, но давит меньшинства) |
| Режим окна | `SMOOTH_PROB_WINDOW` | **0** | резервный: 0 = Viterbi; >0 = бегущее окно ±N/2 сек |
| Пауза визита | `SMOOTH_GAP_SEC` | **10** | пауза > 10с → новый проход (замер gap 5..60 → плато с 10) |
| Гейт | `SMOOTH_GATE` | **0** (выкл) | **КРИТИЧНО:** с гейтом 0.8 Viterbi слабее (21.1%) — уверенные-но-неверные не флипаются |
| Склейка зон | `SMOOTH_MERGE_ZONES` | **0** (выкл) | склеить зоны `d`/`u` ОДНОЙ камеры в один поток по времени. С Viterbi эффект в пределах шума (v3 −0.17пп) |
| Жёсткий голос | `SMOOTH_HARD_VOTE` | **0** (выкл) | ⚠️ **opt-in, НЕ в проде:** 1 класс на весь визит = argmax среднего probs. Откачен: на независимой истине хуже Viterbi (см. ниже) |

**Активный алгоритм — Viterbi/HMM БЕЗ гейта.** Приоритет режимов в `smooth_sequence`:
**`HARD_VOTE` → окно (`PROB_WINDOW>0`) → Viterbi**; в проде включён только Viterbi. Предохранители
(`guard`/`min-minority`/`veto`) и `P_STAY`/`GATE` — только для Viterbi. Параметры окна (`SMOOTH_PROB_WINDOW_K`,
`_TRI`) — только для режима окна. Флаги читаются per-poll из `.env` (см. `_build_args` в `3b`/`4b` `.sh`) →
смена без рестарта. `4b` (идентификация) наследует те же `SMOOTH_*` — при желании развести отдельными `SMOOTH_ID_*`.

**Группировка кадров для сглаживания = по «камере», потом на визиты по времени** (`temporal_smooth.smooth_sequence`).
«Камера» из имени файла ВКЛЮЧАЕТ суффикс зоны (`cam_01_9_d` / `cam_01_9_u`) — т.е. две кроп-зоны одной
физической камеры сглаживаются РАЗДЕЛЬНО, и проход человека между зонами рвётся на два визита.
`SMOOTH_MERGE_ZONES=1` снимает суффикс зоны → зоны одной камеры идут одним потоком по времени (разные
физ. камеры `cam_01`/`cam_02` остаются раздельными). **С Viterbi эффект в пределах шума** (v3 −0.17 п.п.)
→ по умолчанию ВЫКЛ.

**Свип методов/гиперпараметров.** ⚠️ **ВЫВОД ЗАВИСИТ ОТ ИСТИНЫ — это стоило разобрать.** Полный каталог
измеримых блоков (v1–v4, ~46k кропов) и надёжность истины — в [eval_datasets.md](eval_datasets.md).

**Таблица 1 — на `smoothed`-истине (v3-images + v4-smoothed), ⚠️ ЦИКЛИЧНА** (v4-истина сидирована из
выхода сглаживателя → смещена в его пользу; recall на v4):

| Метод | v3 | v4 | recall res/del/utl/gst (v4) |
|-------|----|----|--------|
| baseline (argmax/кроп) | 23.6% | 31.0% | 72/61/48/56 |
| current (Viterbi p_stay=0.9) | 18.8% | 22.9% | 82/62/45/59 |
| Viterbi p_stay=0.99 | 16.8% | 20.8% | 84/60/45/61 |
| окно ±5с | 14.9% | 20.3% | 85/60/35/64 |
| жёсткий голос: 1 класс/визит | 12.9% | 18.2% | 87/62/35/64 |

По таблице 1 жёсткий голос выглядел лучшим. Но `smoothed`-истина хвалит любой сглаживатель. **Перемер на
независимой `images`-истине (раскладка classify + ручные правки, от сглаживателя НЕ зависит) перевернул вывод:**

**Таблица 2 — на независимой `images`-истине** (ошибка + recall res/del/utl/gst):

| Метод | v4 (25.6k, минориты 1180/482/1354) | весь корпус v1–v4 (46k) |
|-------|------------------------------------|--------------------------|
| baseline | 10.7% · 87/97/97/95 | 17.4% · 86/79/43/55 |
| **Viterbi p_stay=0.9** | **7.3%** · **93/93/82/88** | **14.4%** · 91/75/33/49 |

**Выводы:** (1) **на независимой истине Viterbi доминирует жёсткий голос** — ниже ошибка (v4 7.3% vs 10.3%)
И заметно выше recall меньшинств (доставка/ЖКХ/гость 93/82/88 vs 70/58/49). Жёсткий голос по ошибке едва
лучше baseline и **выкашивает меньшинства** — исходное опасение подтвердилось; «победа» из таблицы 1 была
артефактом циклической истины. (2) **Жёсткий голос ОТКАЧЕН из прода** (`SMOOTH_HARD_VOTE=0`), прод —
Viterbi `p_stay=0.9`; режим остаётся в `smooth_sequence` как opt-in для экспериментов. (3) Ни одна истина не
идеальна (`images` смещена к baseline, `smoothed` — к сглаживателю); чистый ранжир требует независимой
human-verified разметки. (4) **oracle ~3% → визиты почти однокласные**, трекинг по персонам — НЕ рычаг
(боксы кропов сохраняются в имени `_b<x1>-<y1>-<x2>-<y2>` для будущих замеров, но потолок задаёт модель).
Направление/`tracker.py` — прототип, не в пайплайне.

Запуск локального замера Viterbi: `python scripts/pipeline/3b_smooth_groups.py <images> --gap 10
--prob-window 0 --gate 0 --p-stay 0.9 [--viz --truth .data/groups/v3/inference/images]`. Резервный
режим — бегущее окно (`--prob-window 6 --prob-window-k 7 --prob-window-tri`, ±3с взвеш; см. таблицу ниже).

### Замеры (v4-инференс на 9429 кропах v3-инференса 12–20, истина = `labels.json`)

`before` = argmax probs модели v4; `after` = сглаженный класс; ошибка = класс ∉ истины. ДО (модель):
**26.2%** ошибок (2470/9429), recall res/del/utl/gst = 0.72/0.93/0.84/0.86.

| Вариант окна | Ошибок | Нетто | Испр/слом | recall res/del/utl/gst |
|--------------|-------:|------:|:---------:|:----------------------:|
| ±1.5с равные веса (`pw3`) | 21.2% (1998) | −5.0 п.п. | 820/348 | 0.78/0.90/0.73/0.85 |
| ±1.5с взвешенное (`pw3 --tri`) | 21.9% (2061) | −4.3 п.п. | 731/322 | 0.77/0.90/0.75/0.86 |
| **±3с равные веса (`pw6`)** | **20.7% (1955)** | **−5.5 п.п.** | 864/349 | 0.79/0.90/0.73/0.85 |
| ±3с взвешенное (`pw6 --tri`) | 21.3% (2007) | −4.9 п.п. | 795/332 | 0.78/0.90/0.75/0.86 |

Окно тянет вверх доминирующего резидента (0.72→0.79) ценой меньшинств (ЖКХ 0.84→0.73). Среди окон
лучший общий — ±3с равные веса (20.7%); взвешенное мягче (сохраннее ЖКХ/гость).

**Viterbi/HMM БЕЗ гейта (АКТИВНЫЙ прод) — заметно лучше окна.** Gate был главным тормозом: с ним
Viterbi ≈ окну (21.1%), без него — резко лучше. `p_stay` — та же ручка «липкость ↔ меньшинства».

| Вариант | Ошибок | Нетто | recall res/del/utl/gst |
|---------|-------:|------:|:----------------------:|
| ±3с окно взвеш (прежний прод) | 21.3% | −4.9 п.п. | 0.78/0.90/0.75/0.86 |
| Viterbi p_stay=0.95 **+gate 0.8** | 21.1% | −5.1 п.п. | — |
| **Viterbi p_stay=0.9 gate=0 (прод)** | **16.9%** | **−9.3 п.п.** | 0.83/0.88/0.75/0.82 |
| Viterbi p_stay=0.95 gate=0 | 16.6% | −9.6 п.п. | 0.83/0.88/0.66/0.82 |
| Viterbi p_stay=0.999 gate=0 | 14.1% | −12.0 п.п. | 0.86/0.88/0.50/0.81 |
| окно→Viterbi (последовательно) | ≥17.7% | — | хуже чистого Viterbi |

`p_stay=0.9` выбран как баланс: 16.9% при сохранённом ЖКХ (0.75, как у окна); выше `p_stay` — лучше
общая, но убивает ЖКХ (→0.50). Последовательная связка окно→Viterbi хуже чистого Viterbi. **Свип
`gap` (Viterbi p_stay=0.9): 5→17.2%, 10→16.9%, 20..60→плато 16.9%** — переход в Viterbi времени не
учитывает, `gap=10` берёт весь выигрыш, выше — риск сшить разные события зря.

Скорость не важна (офлайн), считается от исходных вероятностей CSV → идемпотентно; сглаживать имеет
смысл СВЕЖИЙ инференс (размеченный вручную — там метки уже истина). Историческое (прежняя семантика
окна-как-радиуса): v3_1 baseline 25.7%→~18%; v4_1 на 20260720 7.0%→3.5%.

**Дебаг-визуализация** (`--viz`, env `SMOOTH_VIZ=1`, на начальном этапе включена): **один конкат на
ПРОХОД** (визит, сегментация по `gap`) с ≥1 исправлением ИЛИ ошибкой — в `smoothed/<date>/smooth_viz/`
(имя — по первому «интересному» кропу прохода). В конкате показаны **ВСЕ кадры прохода** (в т.ч.
НЕ изменённые — чтобы глазами ловить и не исправленные ошибки), ≤41 тайл (центрируются на
исправлениях). Под каждым кадром: **номер по порядку** + время, класс модели (argmax), вероятности,
и снизу зелёным **`w:<номера>`** — в окна каких жёлтых кадров вошёл тайл (когда зелёные окна
нескольких жёлтых сливаются). Рамки: **жёлтая** — исправленные (их может быть несколько); **зелёная** —
тайл в бегущем окне какого-то жёлтого (±окно/2 сек ∩ ±K/2 кадров); **красная** — многолюдные (M>1).
Вертикальная **чёрно-бело-чёрная линия** (сквозь полосу И графики) — разрыв времени больше радиуса окна.
С **`--truth <labels.json|каталог>`** (напр. `.data/groups/v3/inference/images`) помечаются **ошибки
vs истины** (сглаж-класс ∉ метки, в т.ч. НЕ исправленные) — **маджента-уголок + буква истинного класса**;
конкат тогда рисуется и для проходов с ошибками без исправлений (лог: `ошибок vs истины N/неиспр M`).
`smoothed/` не является раскладкой кропов (только метаданные). Выключить: `SMOOTH_VIZ=0` или `--no-viz`.

**Порядок пайплайна и раскладка:** classify (3) → **smooth (3b)** → identify (4).
```
inference/
  images/<date>/     ← НЕИЗМЕНЯЕМО (только classify): single/<class>/, multi/, uncertain/, CSV, labels.json
  smoothed/<date>/   ← 3b: classifications_smoothed.csv (crop,…,smoothed_class,rel,p_*), smooth_state.json,
                        smooth_viz/. labels.json здесь пишет ТОЛЬКО человек (2_label_ui), не сглаживатель
  meta/<date>/<session>/ ← логи classify: ОДИН каталог на сессию сервиса (run.log дописывается);
                           новый — только при рестарте и полночи (не на каждый поллинг)
```
classify раскладывает `images/`; **3b НЕ трогает `images/`** — пишет сайдкар `smoothed/<date>/`; identify
читает `smoothed/<date>/classifications_smoothed.csv` (берёт кропы со `smoothed_class ∈ {1_resident,4_guest}`),
а jpg ищет в `images/` по имени. Выход identify — в ОТДЕЛЬНОМ дереве `.data/residents/v1/inference/`.

**Синхронизация identify ← smooth (watermark).** Без координации identify успел бы опознать «ложного
резидента» (ошибку модели) РАНЬШЕ, чем 3b пересчитает класс. Решение: 3b пишет
`smoothed/<date>/smooth_state.json` = `{csv_rows: N}` (докуда просглажен classifications.csv). identify
(`4_...sh`) берёт дату только когда `csv_rows ≥` текущего числа строк CSV. Env `SMOOTH_WAIT=1` (вкл),
`SMOOTH_WAIT_TIMEOUT=600` — fallback: если CSV не менялся N сек (smooth выключен/отстал), не блокируем.
Нет сайдкара вовсе → identify откатывается на старую физ. раскладку `single/{1_resident,4_guest}`+`multi/`.

**Разметка результата сглаживания.** Сайдкар самодостаточен → `./sh/train/2_label_ui.sh --smoothed
.data/groups/v4/inference/smoothed/<date>` выведет всё сам: кропы из `images/<date>` (INPUT), «текущий
класс» = ручной `smoothed/<date>/labels.json` (LABELS) ЕСЛИ он есть, иначе **сид из `smoothed_class`**
(`classifications_smoothed.csv`), probs оттуда же. Правки разметчика пишутся в `smoothed/<date>/labels.json`
и его пишет ТОЛЬКО разметчик — **сглаживатель labels.json не трогает**, поэтому пересчёты сглаживания не
затирают ручную разметку. Либо разметка модельного выхода — прямо на `images/labels.json` (3b его не трогает).

**Общее ядро (группы и жители).** Логика сглаживания вынесена в `src/common/utils/smooth_core.py`
(параметризовано классами/подписями/цветами). Два тонких драйвера и **два сервиса**:
- `3b_smooth_groups.py` / `video-smooth` — классы Модели 1 (фикс. `GROUP_CLASSES`), вход `classifications.csv`;
- `4b_smooth_identity.py` / `video-smooth-identity` — идентификация Модели 2, вход `identifications.csv`,
  **открытый набор жителей выводится из `p_<person>` колонок**; подписи/цвета авто (палитра), viz top-3
  персоны на тайл. Внутри визита — один человек → сглаживание особенно уместно: единичные флипы личности
  убираются, `unknown_resident` внутри прохода спасается в жителя. Сайдкар — `residents/<ver>/inference/smoothed/<date>/`.
  Замеры отложены (модель Модели 2 пока слабая — сначала дообучение, потом настройка сглаживания).

## Почему две модели с одной архитектурой

| | Модель 1 (группы) | Модель 2 (жители) |
|---|---|---|
| Классы | 1_resident / 2_delivery / 3_utilities | конкретные жители + unknown_resident |
| Множество классов | закрытое, меняется редко | открытое (новый житель = новый класс) |
| Датасет | все группы, данных относительно много | только жители, данных мало |
| Переобучение | редко (новый тип посетителя) | раз в 2–4 недели по мере накопления |

Та же архитектура для обеих потому что:
- вход одинаковый (кроп сверху, тот же ракурс и освещение)
- датасет жителей маленький → более тяжёлый backbone даст переобучение, а не точность
- позволяет использовать трансфер цепочкой (см. ниже)

---

## Почему не cosine similarity по эмбеддингам для жителей

- **Угол камеры сверху** — стандартные ReID-модели обучены на виде сбоку/спереди,
  лицо часто не видно вообще
- **Разная одежда** — appearance-based эмбеддинги кодируют цвет куртки как основной
  признак; тот же человек в другой одежде окажется дальше по косинусному расстоянию,
  чем другой человек в похожей одежде
- **Нет контрольных фото** — у нас только кропы из тех же камер с тем же углом

Классификатор, обученный на накопленных кропах, учит признаки специфичные для нашего
ракурса (силуэт сверху, ширина плеч, форма головы) и с каждым циклом переобучения
становится лучше, включая новые outfit.

## Сборка нового датасета (итеративное улучшение)

После накопления инференса Модели 1 собирается новый датасет для переобучения.
Источники разбиты на стратегии по ценности данных.

### Пороги уверенности

```dotenv
# .env
CLASSIFY_CONF=0.65        # основной порог инференса (conf < → uncertain/)
CLASSIFY_CONF_HIGH=0.85   # второй порог: выше — псевдо-метки, ниже — серая зона
```

### Стратегии отбора

| # | Суть | Источник | Условие | Метка берётся из |
|---|------|----------|---------|-----------------|
| 1 | Ошибка с низкой уверенностью — исправлена вручную | `inference/YYYYMMDD/<class>/` | `labels.json` ≠ subdir, `conf < conf_high` | `labels.json` (ручная переразметка) |
| 2 | Модель не уверена — размечено вручную | `inference/YYYYMMDD/uncertain/` | файл есть в `labels.json` с валидным классом | `labels.json` (ручная разметка) |
| 3 | Серая зона — conf < conf_high, есть метка | `classifications.csv` | `conf < CLASSIFY_CONF_HIGH` И есть `labels.json` | `labels.json` |
| 5 | Уверенная правильная метка — псевдо-лейбл | `classifications.csv` | `conf ≥ CLASSIFY_CONF_HIGH` И pred = true | subdir / `labels.json` |
| 7 | Уверенная ошибка — наиболее ценные примеры | `classifications.csv` | `conf ≥ CLASSIFY_CONF_HIGH` И pred ≠ true | `labels.json` (из стрт 1 с высокой уверенностью) |
| 8 | Граничный случай между двумя классами | `classifications.csv` | `margin = conf_top1 − conf_top2 < порог` | `labels.json` |
| F | Дополнение минорных классов из предыдущего датасета | предыдущий датасет | new\_count < prev\_count | subdir датасета-источника |

Стратегии 1 и 7 выделяются автоматически из одного пула ошибок через `_split_errors_with_quota`:
- `conf ≥ conf_high` → стрт 7 (уверенная ошибка, всегда включается)
- `conf < conf_high` → стрт 1 (неуверенная ошибка, ограничивается дефицит-квотой по классу)

**Стрт 7** — самая ценная: модель уверена, но систематически ошибается. Без таких примеров переобучение не исправит ошибку.

**Стрт 3** покрывает весь диапазон `conf < conf_high` (включая `conf < conf_low`) — все неуверенные случаи, где есть ручная метка. Это же покрывает то, что раньше называлось «стрт 4».

**Стрт 8** (margin sampling): `margin = conf_top1 − conf_top2`. Малый margin — граничный случай между двумя классами. Пример:
```
[0.68, 0.63, 0.05, 0.04]  conf=0.68, margin=0.05  ← брать (граница 4_guest/1_resident)
[0.68, 0.15, 0.10, 0.07]  conf=0.68, margin=0.53  ← не брать (просто немного неуверен)
```


Это позволяет единой системой извлекать из датасетов не только ошибки (стрт 4/7), но и
уверенные правильные примеры (стрт 5), неуверенные (стрт 3), uncertain (стрт 2).

### Фильтры

**Временно́е дедублирование** (стрт 5): не более 1 кропа на (камера, 15-минутное окно).
Применяется только к данным из инференса; для датасетов — `--dedup-min 0`.

**Квота ошибок** (стрт 1/7): `score = conf × (target / current_cls_size)`, где target — geomean
размеров классов в выходном датасете. Стрт 7 (conf ≥ conf_high) всегда включается;
стрт 1 (conf < conf_high) — до дефицита (target − current) штук на класс.

**Квота на класс** (`--max-per-class`): жёсткий лимит поверх всех стратегий.

## Полу-автоматическая разметка датасета жителей

### Проблема diff-фильтра

`filter_residents.py --min-diff 40` убирает похожие соседние кадры — это нужно для датасета,
но делает intra-person дифы (~49 медиана) неотличимыми от inter-person дифов (~61 медиана).
Поэтому прямая полу-авторазметка "по порогу дифа" не работает.

### Решение: сцены

Без diff-фильтра intra-person дифы 5–15, inter-person 30–80 — разделение чистое.
Сцена — непрерывный поток от одного человека (граница = большой разрыв по времени или diff).

### Версионирование

Рабочий каталог задаётся через `.env`:
```dotenv
RESIDENTS_VER=v1   # → .data/residents/v1/scene_pool/
```

Скрипты `1_b_1_collect_scenes.sh` и `1_b_2_propagate_scenes.sh` читают эту переменную автоматически.

### Пайплайн (4 шага)

**Шаг 1_b_1 — Собрать без diff-фильтра, разбить на сцены:**
```bash
./sh/train/residents/1_b_1_collect_scenes.sh
# Опции:
#   --scene-gap 120   # разрыв >120s → новая сцена
#   --scene-diff 50   # pixel-diff >50 → новая сцена (только по времени: --scene-diff 0)
#   --min-blur 40     # убираем совсем размытые
#   --dry-run         # только статистика, без копирования

# Выход: .data/residents/$RESIDENTS_VER/scene_pool/
#   *.jpg               — все кандидаты (без diff-фильтра)
#   scenes.json         — сцены: scene_id, cam, date, frames[], representative
#   representatives/    — по 1 резкому кадру на сцену → для ручной разметки
```

Входные каталоги прописаны явно в `SOURCES=(...)` внутри скрипта.
Для добавления новой даты — раскомментировать строку или добавить `--src`.

**Перенос существующих меток (опционально, перед шагом 2):**

Если есть уже размеченный пул (например, `.data/residents/v0/new_labeld/labels.json`),
метки можно перенести в scene_pool двумя способами:
1. По имени файла — прямое совпадение
2. По (cam, date, sod) — файл из старого пула попадает во временной диапазон сцены → метка присваивается representative сцены

После переноса запустить `1_b_2_propagate_scenes.sh` для распространения.

**Шаг 2 — Разметить representatives/ (по 1 кадру на сцену):**
```bash
./sh/train/2_label_ui.sh \
    --input   .data/residents/v1/scene_pool/representatives \
    --labels  .data/residents/v1/scene_pool/labels.json \
    --dataset .data/residents/v1/dataset \
    --unlabeled-only
# Кадры из representatives/ имеют вид: scene0042_cam01_9_d_...conf0.85.jpg
# Кнопки берутся из подпапок --dataset (реальные классы: 141_resident_man_1, ...)
# labels.json — в корне scene_pool, НЕ в representatives/
```

**Шаг 1_b_2 — Авторазметка внутри сцен:**
```bash
./sh/train/residents/1_b_2_propagate_scenes.sh
# Опции:
#   --intra-diff 25   # кадры с diff>25 от representative → не распространять
#   --dry-run         # только статистика

# Читает: scene_pool/scenes.json + scene_pool/labels.json
# Пишет: дополняет scene_pool/labels.json для всех кадров сцены
# Конфликт (2 метки в одной сцене) → сцена пропускается, выводится предупреждение
# Имена с префиксом scene0042_ (из representatives/) автоматически нормализуются
```

При необходимости шаги 2 и 1_b_2 повторяются для граничных / проблемных сцен.

**Шаг 1_b_3 — Финальный diff-фильтр для разнообразия в датасете:**
```bash
./sh/train/residents/1_b_3_filter_scenes.sh
# Дефолты: --min-diff 40, путь из RESIDENTS_VER
# Опции:
#   --min-diff 30     # другой порог
#   --dry-run
```

### Структура выхода

```
.data/residents/
  v1/
    scene_pool/
      *.jpg                — кандидаты (без diff-фильтра, все кадры)
      scenes.json          — сцены: scene_id, cam, date, frames[], representative
      representatives/     — scene0001_<name>.jpg  ← размечать только эти
      labels.json          — {"version":1, "labels":{...}}  ручные + авто-метки
    dataset/
      141_resident_man_1/  — после финального фильтра, готово для обучения
      141_resident_woman_1/
      ...
```

### Конфликты и граничные случаи

- **Несколько person_id в одной сцене** — `propagate_scenes.py` выводит предупреждение
  и пропускает сцену. Решение: уменьшить `--scene-diff` в шаге 1_b_1 и пересобрать.
- **Смена одежды в длинной сцене** — если diff не изменился, авторазметка правильная
  (одна сцена = один человек). Проверить визуально gallery в label_ui.
- **Несколько человек подряд без разрыва** — сцена может быть "загрязнена".
  `--intra-diff N` в шаге 1_b_2 отсечёт кадры с большим отклонением от representative.

**Параметры:**

**Обработка дисбаланса классов:**

Оба флага включены по умолчанию — актуально при дисбалансе (текущий датасет ~15:1).

- `WeightedSampling` — `WeightedRandomSampler`: равномерная выборка из каждого класса в батче
- Разбивка train/val — **стратифицированная**: `val_split` % берётся из каждого класса отдельно

**Фазы обучения:**
1. Эпохи 1 → N/2: обучается только классификационная голова (backbone заморожен)
2. Эпохи N/2+1 → N: размораживается вся сеть, lr × 0.1

Гости включены — они тоже ходят в конкретные квартиры и идентифицируемы.

### Inference output (4_identify_residents.py)

```
.data/residents/v1/inference/
  images/
    20260712/
      141_resident_man_1/   ← опознан с conf ≥ IDENTIFY_CONF
      unknown_resident/     ← conf < IDENTIFY_CONF
      identifications.csv   ← все кропы: person_id, id_conf, probs по классам
      labels.json           ← для label_ui: person_id → label
                               опознанные: "141_resident_man_1"
                               unknown_resident: "" (пустая строка = нужна ручная разметка)
```

Скрипт принимает на вход `1_resident` **и** `4_guest` из classify-output: гости прогоняются
через Модель 2, чтобы поймать случаи когда Модель 1 ошиблась.

### Сбор и фильтрация кропов

```bash
# Шаг 1: собрать кропы
./sh/train/residents/1_collect_residents.sh
#   --out .data/residents/v0/new   (default)
#   --interval 1                   (1с окно на камеру, default)
#   --conf-delta 0.1               (из окна брать все кадры с conf ≥ max-0.1, default)
#   --max-persons 1                (только кадры где один человек, default)
#   --classes 1_resident 4_guest   (default)

# Шаг 1а: (опционально) анализ пула до дедупликации
./sh/train/residents/3_analyze_pool.sh
#   --interval 2   (размер окна для статистики)
#   --out .data/residents/v0/analysis
# → графики: frames_per_window, conf_distribution, pixel_diff

# Шаг 2: отфильтровать плохие кропы
./sh/train/residents/2_filter_residents.sh
#   --min-conf 0.5      (conf Model 1 из имени файла, default)
#   --min-blur 40       (резкость по дисперсии Лапласиана, default)
#   --yolo-persons 1    (max людей в кропе по YOLO, default; conf=0.12)
#   --min-coverage 0.15 (min доля кадра под bbox человека, default)
#   --min-diff 20       (pixel-diff фильтр: следующий кадр той же камеры/даты
#                        берётся только если mean-abs-diff от предыдущего ≥ N, default)
#   --min-body 0        (доля видимого тела по pose, default=отключён)
```

Фильтры убирают: кадры с несколькими людьми (YOLO пропустил слияние bbox),
motion blur, низкий confidence Модели 1, кропы где детектор не нашёл человека,
и похожие соседние кадры (`--min-diff`).

`--min-diff` — жадный greedy-алгоритм: кадры группируются по `(cam, date)`, сортируются
по времени. Следующий кадр добавляется только если mean-abs-diff от последнего оставленного
≥ порога. Работает глобально по дню, не ограничен окном из шага 1.

`--min-body` требует `yolov8n-pose.pt` (`.models/detect/`). Pose estimation даёт
долю видимых keypoints из 17 (COCO). Из-за вида камеры сверху даже хорошие кадры
дают ~35–65%, поэтому порог ставить не выше 0.25.

```bash
# Посмотреть что будет удалено без реального удаления:
./sh/train/residents/2_filter_residents.sh --dry-run
./sh/train/residents/2_filter_residents.sh --dry-run --min-diff 30
```

### Разметка

```bash
# Дефолт — жители (v0/new → v1/dataset)
./sh/train/2_label_ui.sh

# Явно указать пути
./sh/train/2_label_ui.sh --input .data/residents/v0/new --dataset .data/residents/v1/dataset
```

Классы (`person_01`, `person_02`, …) читаются из подпапок `v1/dataset/` автоматически.
Чтобы добавить нового человека — создать папку `person_NN/` и обновить страницу в браузере.

### Переобучение

Цикл переобучения — раз в 2–4 недели или при добавлении нового жителя.
Всегда обучать на **полном накопленном датасете** (иначе catastrophic forgetting).

```
Цикл 1:  backbone Модели 1  → обучение на {неделя 1}       → Модель 2 v1
Цикл 2:  Модель 2 v1        → обучение на {неделя 1 + 2}   → Модель 2 v2
Цикл 3:  Модель 2 v2        → обучение на {неделя 1+2+3}   → Модель 2 v3
```

```bash
# Первый цикл — backbone от Модели 1
./sh/train/residents/5_train_residents.sh --data .data/residents/v1/dataset --backbone .models/classify/backbone.pt

# Последующие циклы — веса предыдущей версии
./sh/train/residents/5_train_residents.sh --data .data/residents/v1/dataset --init-from .models/identify/v1.pt
```

### Добавить нового жителя

```
1. Запустить 1_collect_residents.sh + 2_filter_residents.sh (подберут новые кропы)
2. Создать папку .data/residents/v1/dataset/person_NN/
3. Разметить новые кропы через 2_label_ui.sh
4. Переобучить Модель 2 на полном датасете (--init-from предыдущей версии)
```

До переобучения новый житель попадёт в `unknown_resident`.

### Трансфер между моделями

```
ImageNet weights
    ↓
fine-tune на датасете групп (1_resident / 2_delivery / 3_utilities)
    ↓
Модель 1  (.models/classify/v1_1.onnx)
    │
    └── backbone.pt (только features, без головы)
            ↓
        fine-tune на датасете жителей
            ↓
        Модель 2 v1  (.models/identify/v1.onnx)
            ↓ (от неё же)
        Модель 2 v2  (.models/identify/v2.onnx)
```
