# Техническое описание системы видеонаблюдения и распознавания людей

## 1. Общее описание

Система реального времени для анализа видеопотоков с 4 IP-камер iCSee (8MP, Wi-Fi, RTSP). Выполняет поэтапное распознавание людей: 
- первичное обнаружение, 
- классификацию по группам 
- и индивидуальную идентификацию жителей. 

Работает на CPU без GPU. Результаты фиксируются в базе данных и доступны через Telegram-бот.

---

## 2. Камеры

**Модель:** iCSee, уличная поворотная PTZ, 8MP (2048×1080), H.264/H.265, IP66

**Количество:** 4 камеры (2 модели одного производителя)

**Подключение:** только Wi-Fi

**Расположение:**
- Камера 1 — тот же роутер, что и сервер (домашняя сеть, прямой доступ)
- Камеры 2–4 — разные роутеры на разных этажах (отдельные подсети)

### 2.1 Подключение к потоку RTSP

Камеры поддерживают RTSP напрямую. Формат URL:

```
rtsp://<IP>:554/user=<USER>&password=<PASSWORD>&channel=1&stream=0.sdp?real_stream
```

- `stream=0` — основной поток (2048×1080, до 25 fps)
- `stream=1` — субпоток (пониженное разрешение, рекомендуется для анализа)

Дополнительные порты камеры:
| Протокол | Порт  |
|----------|-------|
| RTSP     | 554   |
| HTTP     | 80    |
| ONVIF    | 8899  |
| DVRIP    | 34567 |

### 2.2 Проблема сетевой доступности (камеры 2–4)

Камеры 2–4 находятся за отдельными роутерами — прямое обращение по IP невозможно без дополнительной настройки.

**Варианты решения (в порядке предпочтения):**

| Вариант | Сложность | Надёжность | Описание |
|---------|-----------|------------|----------|
| **Port forwarding** | низкая | средняя | На каждом роутере пробросить порт 554 → IP камеры. Доступ через внешний IP роутера |
| **WireGuard VPN** | средняя | высокая | Объединить все роутеры в одну VPN-сеть, сервер видит все камеры напрямую |
| **go2rtc прокси** | средняя | высокая | Лёгкий RTSP/WebRTC прокси, устанавливается рядом с каждым роутером (на Pi или прошивке) |
| **P2P (DVRIP)** | высокая | низкая | Проприетарный протокол iCSee через облако — не рекомендуется для production |

**Рекомендация:** WireGuard VPN между роутерами. Сервер входит в VPN-сеть и видит все 4 камеры по внутренним IP.

### 2.3 Параметры видеопотока для анализа

Для анализа использовать субпоток (`stream=1`) — снижает нагрузку на CPU при захвате. Разрешение субпотока обычно 640×360 или 1280×720 — достаточно для детекции людей.

Основной поток (`stream=0`, 2048×1080) — для сохранения кадров-событий в высоком качестве.

## 4. ML-пайплайн

### 4.1 Общая схема (один кадр)

```
Кадр с камеры (субпоток, напр. 640×360)
      │
      ▼
┌──────────────────────────────────────────────┐
│  МОДЕЛЬ 1: Детекция людей                    │
│  YOLOv8n (ONNX) — вся сцена целиком          │
│  Выход: список bounding boxes людей          │
└─────────────────────┬────────────────────────┘
                      │
          ┌───────────┴──────────┐
     0 человек               1+ человек
          │                      │
     пропустить              для каждого bbox:
     кадр                    crop + resize → 224×224
                                  │
                                  ▼
              ┌───────────────────────────────────────┐
              │  МОДЕЛЬ 2: Классификация группы       │
              │  MobileNetV3-Small (ONNX)             │
              │  Классы: resident / courier /         │
              │          delivery / utilities / other │
              └──────────────────┬────────────────────┘
                                 │
              ┌──────────────────┴─────────────────┐
         class = resident                    class ≠ resident
              │                                    │
              │                             confidence ≥ threshold?
              │                             ├─ нет → unclassified_groups
              │                             └─ да → записать событие
              │                                    (group_class, без person_id)
              ▼
┌─────────────────────────────────────────────────────┐
│  МОДЕЛЬ 3a: Детекция лица (RetinaFace lite / ONNX)  │
│  Выход: face bbox (если лицо видно)                 │
└──────────────────────┬──────────────────────────────┘
                       │
         ┌─────────────┴──────────────┐
     лицо найдено               лицо не найдено
         │                           │
         ▼                     использовать только
┌─────────────────────┐        crop по всему телу
│  face crop + align  │              │
└──────────┬──────────┘              │
           └──────────┬──────────────┘
                      ▼
        ┌─────────────────────────────────┐
        │  МОДЕЛЬ 3b: Идентификация       │
        │  MobileFaceNet (ONNX)           │
        │  Face/body embedding → cosine   │
        │  similarity с базой жителей     │
        └─────────────┬───────────────────┘
                      │
          ┌───────────┴──────────────┐
    sim ≥ threshold              sim < threshold
          │                           │
    записать событие            unclassified_persons
    (person_id, confidence)
```

### 4.2 Обработка нескольких людей на кадре

Каждый человек из bounding boxes обрабатывается **независимо**. Дополнительно:

- Все люди из одного кадра связаны полем `frame_group_id` в таблице событий.
- Если на кадре несколько жителей идентифицированы одновременно — они могут быть помечены как «совместный проход» (например, семья из одной квартиры). Логика:
  - два и более жителя из одной квартиры (поле `apartment_id` в `persons`) появились на одном кадре → событие типа `group_pass`
  - удобно для отчётности и дообучения

### 4.3 Рекомендуемые модели (CPU-only)

| Задача | Модель | Размер | Скорость на CPU* | Точность |
|--------|--------|--------|-----------------|----------|
| Детекция людей | YOLOv8n | ~6 MB | ~20–40 мс/кадр | достаточная |
| Классификация группы | MobileNetV3-Small | ~10 MB | ~5–10 мс/crop | хорошая |
| Детекция лица | RetinaFace-MobileNet | ~1.6 MB | ~10 мс | хорошая |
| Идентификация | MobileFaceNet | ~4 MB | ~5 мс/лицо | хорошая |

*Оценка для современного CPU (i5/i7), одно изображение, ONNX Runtime.

Все модели экспортируются в **ONNX** — единый рантайм, не требует PyTorch/TF в production.

## 5. Сервисы

### 5.1 Backend (FastAPI)

**Технологии:** Python 3.11+, FastAPI, OpenCV, asyncio

**Ответственности:**
- Захват субпотока RTSP с каждой камеры (`cv2.VideoCapture` в отдельном потоке)
- Семплирование кадров (1–5 FPS, настраиваемо)
- Оркестрация ML-пайплайна (async HTTP вызовы в ML Service)
- Сохранение событий в MongoDB и кадров на диск
- REST API для Telegram Bot

**Эндпоинты (для Telegram Bot):**
```
GET  /events                  — список событий (фильтр: камера, класс, дата, person_id)
GET  /events/{id}             — детали события + URL изображения
GET  /events/{id}/image       — бинарник изображения
GET  /persons                 — список жителей
GET  /persons/{id}            — профиль жителя + его изображения
GET  /unclassified            — неидентифицированные записи (для разметки)
POST /persons                 — добавить жителя
POST /persons/{id}/images     — добавить эталонное фото жителя
PATCH /unclassified/{id}      — назначить person_id вручную (разметка)
POST /training/export         — сформировать и скачать zip с выборкой
GET  /cameras                 — список камер и статус подключения
```

---

### 5.2 ML Service (FastAPI + ONNX Runtime)

**Технологии:** Python 3.11+, FastAPI, ONNX Runtime, OpenCV, NumPy

**Принцип работы:** изображение приходит как `bytes` по multipart, декодируется в numpy array в памяти, подаётся в модель. Ничего не пишется на диск в режиме inference.

**Эндпоинты — Inference:**
```
POST /inference/detect
  body: image (bytes, multipart)
  response:
  {
    "persons": [
      { "bbox": [x1, y1, x2, y2], "confidence": 0.91 }
    ]
  }

POST /inference/classify
  body: image (bytes, multipart)   — crop одного человека
  response:
  {
    "class": "resident",           — resident|courier|delivery|utilities|other
    "confidence": 0.87
  }

POST /inference/identify
  body: image (bytes, multipart)   — crop одного человека (лицо или тело)
  response:
  {
    "person_id": "p_0042",         — null если не распознан
    "confidence": 0.83,
    "method": "face"               — face|body
  }
```

**Эндпоинты — Training:**
```
POST /training/run
  body:
  {
    "model": "detect|classify|identify",
    "images_dir": "/data/training/images",
    "labels_file": "/data/training/labels.json"
  }
  response: { "job_id": "abc123", "status": "started" }

GET  /training/status/{job_id}
GET  /models                        — список версий
POST /models/{model_type}/activate  — активировать версию
```

**Формат labels.json:**
```json
{
  "version": "1.0",
  "task": "classify",
  "classes": ["resident", "courier", "delivery", "utilities", "other"],
  "labels": [
    { "image": "img_001.jpg", "class": "courier", "person_id": null },
    { "image": "img_002.jpg", "class": "resident", "person_id": "p_0042" }
  ]
}
```

## 7. Пороги уверенности (config.yaml)

```yaml
thresholds:
  detection:
    min_confidence: 0.55      # детекция человека в кадре
  classification:
    min_confidence: 0.65      # классификация группы
  identification:
    min_confidence: 0.75      # индивидуальная идентификация жителя

sampling:
  fps: 2                      # анализировать 2 кадра в секунду на камеру
  substream: true             # использовать субпоток для анализа
```

## 10. Сетевая конфигурация и доступ к камерам

### 10.1 Топология

```
[Камера 1] ──── [Домашний роутер] ──── [Сервер разработки, Windows]
                       │
                  Интернет
                       │
[Камеры 2–4] ── [Внешний роутер] ─────────────────────────────────
                       │
                  Интернет
                       │
                 [Прод-сервер, Linux] ←── БД MongoDB
```

### 10.2 IP-адреса камер — как узнать

1. **Через приложение iCSee**: Device → Device Info → IP Address
2. **Через роутер**: DHCP-таблица в интерфейсе роутера, MAC-адрес камеры обычно начинается на `DC:` или `AC:` (производитель XMTech/Dahua)
3. **nmap сканирование** локальной подсети:
   ```bash
   nmap -p 554,8899,34567 192.168.1.0/24
   ```
   — открытые порты 554 или 8899 = iCSee камера

### 10.3 Логин и пароль камеры

По умолчанию: `admin` / (пустой пароль) или `admin` / `admin`

Пароль задаётся при первой настройке в приложении iCSee. Если неизвестен — сброс физической кнопкой на камере.

**Безопасное хранение** в проекте: файл `.env` (в `.gitignore`):
```
CAM_01_URL=rtsp://192.168.1.101:554/user=admin&password=XXXX&channel=1&stream=1.sdp?real_stream
CAM_02_URL=rtsp://...
CAM_03_URL=rtsp://...
CAM_04_URL=rtsp://...
```

### 10.4 Доступ к камерам 2–4 (за внешним роутером)

Камеры 2–4 — за роутером с выходом в интернет. Самый простой вариант — **port forwarding** на этом роутере:

```
Внешний роутер:
  порт 5541 → 192.168.X.X:554  (камера 2)
  порт 5542 → 192.168.X.X:554  (камера 3)
  порт 5543 → 192.168.X.X:554  (камера 4)

RTSP URL с сервера:
  rtsp://<внешний_IP_роутера>:5541/user=admin&password=XXXX&channel=1&stream=1.sdp?real_stream
```

> Прод-сервер обращается к камерам через внешний IP роутера + проброшенный порт.

### 10.5 Почему P2P (DVRIP) не рекомендуется для production

iCSee Android-приложение работает именно через **DVRIP/P2P** — это проприетарный протокол производителя (XMTech), трафик идёт через облачные серверы в Китае.

Проблемы для production:
- **Надёжность**: зависит от доступности стороннего облака — если сервис упадёт, камеры недоступны
- **Задержка**: трафик делает лишний хоп через Китай (+100–300 мс)
- **Безопасность**: видеопоток проходит через серверы третьей стороны
- **Лимиты**: производитель может ограничить одновременные соединения
- **Отладка**: нет документации, протокол закрытый

Для разработки и тестирования DVRIP допустим (есть Python-библиотека `dvrip`), но в production — только прямой RTSP.

## 11. Логика обработки видеопотока

### 11.1 Требования к скорости

Real-time обработка **не требуется**. Система ориентирована на точность:
- Допустимая задержка между проходом человека и записью события: несколько секунд
- Важнее не пропустить событие и правильно идентифицировать, чем скорость реакции

### 11.2 Фильтрация одинаковых кадров (frame diff)

Перед детекцией проверяем, отличается ли новый кадр от предыдущего. Это **очень быстрая операция** — ~0.5–2 мс на CPU.

```python
import cv2
import numpy as np

def frames_differ(frame1, frame2, threshold=5.0) -> bool:
    # Уменьшаем до 160×90 — достаточно для сравнения, быстрее
    f1 = cv2.resize(frame1, (160, 90))
    f2 = cv2.resize(frame2, (160, 90))
    # Переводим в grayscale
    g1 = cv2.cvtColor(f1, cv2.COLOR_BGR2GRAY)
    g2 = cv2.cvtColor(f2, cv2.COLOR_BGR2GRAY)
    # Mean absolute difference
    diff = np.mean(np.abs(g1.astype(float) - g2.astype(float)))
    return diff > threshold  # threshold подбирается эмпирически (5–15)
```

Операция на numpy array 160×90 = ~14 400 пикселей — выполняется быстрее любой ML-модели.

**Параметр `threshold`** подбирается по камере: ночью шум матрицы даёт фоновые изменения ~2–3, движение человека — ~10–30.

### 11.3 Встроенная детекция движения камеры

iCSee камеры поддерживают **Motion Detection** на борту. При срабатывании камера может:
- Отправить push-уведомление (через облако iCSee — неудобно для нашего сервиса)
- Записать на SD-карту

**Использовать встроенную детекцию как основной триггер не рекомендуется** — нет надёжного способа получить события без DVRIP/облака. Лучше реализовать frame diff на стороне сервера (раздел 11.2) — это даёт полный контроль над чувствительностью.

### 11.4 Логика принятия решения по последовательности кадров

Одиночный кадр может дать ложный результат (человек частично в кадре, смаз, плохое освещение). Решение принимается по **скользящему окну** из нескольких кадров:

```
Кадры:     K1    K2    K3    K4    K5    K6
Детекция:  ✓     ✓     ✗     ✓     ✓     ✓
```

**Правило фиксации события:**
- Событие создаётся, когда детекция сработала в ≥ N из последних M кадров (например, 3 из 5)
- Параметры N и M — настраиваемые

**Правило окончания события:**
- Если детекция не срабатывает K кадров подряд — человек ушёл, событие закрыто
- Один проход = одно событие, даже если детекций было много

**Идентификация по окну кадров:**
- По всем кадрам события собираются результаты идентификации
- Финальный person_id = большинство голосов (voting) с минимальным порогом confidence
- Если несколько человек — каждый трекается отдельно (по пересечению bbox)

```yaml
# config.yaml
temporal:
  detection_window_size: 5      # M — размер окна
  detection_min_hits: 3         # N — минимум срабатываний в окне
  event_end_silence_frames: 10  # кадров без детекции = конец события
```
