## 1. Алгоритм motion diff

### Что такое diff

`diff = mean_abs_diff(prev_gray, cur_gray)`

где `prev_gray` и `cur_gray` — последовательные кадры LOW-потока, преобразованные в:
- оттенки серого (`cv2.cvtColor(BGR → GRAY)`)
- уменьшенные до ширины `compare_width=320` пикселей

Формула:  
`diff = mean( abs( prev_gray - cur_gray ) )`  
Результат: **среднее абсолютное изменение яркости** (0–255) по всем пикселям.

### Два потока

| Поток | Назначение | Разрешение | Как читается |
|-------|-----------|------------|-------------|
| **LOW** (`stream=1`) | Детекция движения | ~640×360 | `VideoCapture.read()` в основном цикле |
| **HI** (`stream=0`) | YOLO-детекция людей | ~2304×1296 (→×0.5 = 1152×648) | `StreamReader` (фоновый поток) |

### Что с чем сравнивается

```
LOW кадр N-1  ──┐
                ├─→ mean_abs_diff → diff
LOW кадр N    ──┘
                     │ diff > threshold?
                     ├─→ НЕТ: обновляем baseline (prev = cur), ждём следующий кадр
                     └─→ ДА: берём последний HI-кадр из StreamReader → YOLO
```

### Категории diff в анализе (`4_diff_analysis.py`)

| Категория | Файл-источник | Когда появляется |
|-----------|--------------|-----------------|
| `low_diff` | `raw/{stem}_low_diff{N}.jpg` | HI недоступен (stream recovery), YOLO запускается на LOW как fallback |
| `raw_diff` | `raw/{stem}_raw_diff{N}.jpg` | HI доступен, YOLO ещё не запущен (--save-raw режим) |
| `detected` | `{stem}_low_p{N}.jpg` или `_p{N}.jpg` | YOLO обнаружил человека; diff берётся из ближайшего raw-файла (±3 сек) |

### Интерпретация графиков

**Что видно на графике `low_diff`:**
- Пик на 32–35: характерный артефакт «разморозки» потока после сна/обрыва. Камера отдаёт замороженный кадр → накапливает baseline → при восстановлении получается резкий скачок. **Это не люди, это HEVC-артефакт.**
- Хвост 6–25: реальное движение (ветер, освещение, проходящие люди)

**Что видно на графике `detected`:**
- Медиана ≈22: когда YOLO обнаруживал человека, diff в этот момент был около 20–22
- Это полезная информация для выбора порога: **порог ~20 захватит большинство реальных событий**

**Что видно на графике `raw_diff`:**
- Большой пик 6–11: фоновый шум в нормальном HI-потоке
- Длинный хвост 30–108: крупные события (свет, движение)

### Рекомендуемые пороги

| Ситуация | Порог | Обоснование |
|----------|-------|------------|
| Стабильный поток (исправлен HEVC) | **18–22** | Ниже медианы low_diff-шума, захватывает людей |
| Нестабильный поток (старое поведение) | **35–40** | Выше основного пика stream-thaw артефактов |
| Только реальные крупные события | **50+** | Пропустит большинство людей |

## Запуск скриптов

Все скрипты запускаются в окружении `conda_video` через PowerShell.

### Форегранд (синхронно, вывод в терминал)

```powershell
$env:PYTHONUTF8="1"
conda run -n conda_video python scripts/bench/1_fps_bench.py --duration 60 ...
```

`PYTHONUTF8=1` нужен для корректного вывода кириллицы (иначе UnicodeEncodeError в cp1252).  
Вывод сразу в терминале. Ctrl+C прерывает.

### Фон (запуск, мониторинг из файла)

`conda run` в фоновом режиме не работает (exit 255). Нужно вызывать Python напрямую с флагом `-u`:

```powershell
# 1. Переменные
$env:PYTHONUTF8="1"
$py = "C:\Users\<username>\miniconda3\envs\conda_video\python.exe"
$out = "C:\Users\<username>\AppData\Local\Temp\bench_run.txt"
$err = "C:\Users\<username>\AppData\Local\Temp\bench_err.txt"

# 2. Запуск (флаг -u = unbuffered, иначе файл будет пустым пока скрипт не закончится)
$proc = Start-Process -FilePath $py `
    -ArgumentList @('-u', 'scripts/bench/1_fps_bench.py', '--duration', '60', ...) `
    -RedirectStandardOutput $out -RedirectStandardError $err `
    -NoNewWindow -PassThru
$proc.Id   # сохранить PID

# 3. Мониторинг прогресса (в другом терминале или через Bash-инструмент)
tail -f /c/Users/<username>/AppData/Local/Temp/bench_run.txt

# 4. Проверка ошибок
Get-Content $err

# 5. Остановить (если нужно)
Stop-Process -Id $proc.Id -Force
```

**Почему флаг `-u` обязателен:** без него Python буферизует stdout при записи в файл и файл остаётся пустым всё время выполнения. С `-u` каждая строка `print()` сразу попадает в файл.

## Скрипты замеров

### `1_fps_bench.py` — FPS пропускная способность

```
python scripts/bench/1_fps_bench.py --duration 60 --yolo-warmup 20 --yolo-iters 100 \
    --yolo-max-fps 0.33 --hi-decode-max-fps 1.0 --step-pause-s 15
```

Измеряет **9 шагов** последовательно (одна камера, один поток одновременно):

| Шаг | Что замеряется | Функция |
|-----|---------------|---------|
| **[1/9]** LOW raw | `cap.read()` в цикле, без декодирования/анализа | `bench_low_stream` |
| **[2/9]** LOW + plausible + diff | `cap.read()` → `frame_decode_plausible` → `prepare_gray` → `mean_abs_diff` | `bench_low_with_diff` |
| **[3/9]** HI raw | то же самое что шаг 1, но URL HI-потока | `bench_low_stream` |
| **[4/9]** HI + plausible + diff | то же самое что шаг 2, но URL HI-потока (без resize) | `bench_low_with_diff` |
| **[5/9]** YOLO inference | `n_warmup` прогрев + `n_iters` замер для каждого разрешения | `bench_yolo` |
| **[6/9]** Pipeline A | LOW (read+plausible+diff) + HI `cap.grab()` без декодирования | `bench_pipeline_grab_only` |
| **[7/9]** Pipeline B | Pipeline A + HI `cap.retrieve()` + plausible **на каждом** LOW-кадре | `bench_pipeline_selective_decode` |
| **[8/9]** Pipeline C | Pipeline B + YOLO **на каждом** plausible HI (без ограничений) | `bench_pipeline_full_yolo` |
| **[9/9]** Pipeline C+лимиты | То же с `--yolo-max-fps` и `--hi-decode-max-fps`: YOLO и HI-decode ограничены по fps | `bench_pipeline_full_yolo(hi_decode_max_fps=…, cooldown_s=…)` |

На каждом шаге также замеряется **загрузка ЦПУ** (`psutil.cpu_percent()`, mean и max).  
Между шагами вставляется пауза `--step-pause-s` (по умолчанию 15 сек) — CPU остывает, фоновые процессы успокаиваются.

> **Важно:** HI замеряется тем же методом что и LOW (`cap.read()` напрямую, не через `StreamReader`).  
> Pipeline B и C декодируют HI-кадр **на каждой итерации** — без гейтинга по motion threshold. Это измеряет максимальную нагрузку при постоянном движении.

**YOLO warmup:** каждый вариант (LOW-разрешение, HI-разрешение) получает одинаковое количество прогревочных итераций перед замером, чтобы CPU Turbo Boost успел выйти на устойчивый режим.

**Ключевые параметры:**

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `--duration` | 20 | Длительность каждого из 9 шагов (сек) |
| `--yolo-warmup` | 10 | Прогрев YOLO (итераций на размер) |
| `--yolo-iters` | 50 | Измерительные итерации YOLO (на размер) |
| `--threshold` | 6.0 | Порог motion diff для подсчёта triggers в пайплайнах |
| `--compare-width` | 320 | Ширина уменьшения для mean_abs_diff |
| `--yolo-max-fps` | 0.0 | Шаг [9/9]: макс. частота YOLO (fps). 0=без лимита. Пример: `0.33` = раз в 3 сек |
| `--hi-decode-max-fps` | 0.0 | Шаг [9/9]: макс. частота декодирования HI (fps). Пример: `1.0` = раз в 1 сек |
| `--step-pause-s` | 15.0 | Пауза между шагами (сек). CPU остывает, фоновые процессы успокаиваются |
| `--skip-pipeline` | — | Пропустить шаги 6–9 |

**Рекомендуемые значения лимитов** (на основе бенчмарка, CAM_01_9_D):

| Лимит | Параметр | Значение | Обоснование |
|-------|---------|---------|------------|
| HI decode | `--hi-decode-max-fps` | `1.0` | Фактическая скорость HI plausible = 2.4 fps при 100% CPU; лимит 1 fps освобождает CPU |
| YOLO (надёжно) | `--yolo-max-fps` | `0.33` | = раз в 3 сек; гарантированно > YOLO p95=1.6s под нагрузкой |
| YOLO (баланс) | `--yolo-max-fps` | `0.5` | = раз в 2 сек; выше YOLO mean=1.1s, небольшой запас |
| YOLO (холодный CPU) | `--yolo-max-fps` | `1.0` | = раз в 1 сек; YOLO mean ~380ms, нагрузки мало |
| Без ограничений | любой параметр | `0` | Шаги [1/9]–[8/9] работают без лимитов |

**Выходные данные:**

```
.output/bench/1_fps/run_YYYYMMDD_HHMMSS_msk/
├── fps_report.json   — все числа + параметры запуска
└── fps_charts.png    — 6 графиков (2×3)
```

**Графики (2×3):**
- *top-left* — FPS по этапам: LOW raw / plausible / diff + HI raw / plausible / diff
- *top-center* — YOLO inference: mean и p95 для каждого разрешения (мс + fps на столбцах)
- *top-right* — **Загрузка ЦПУ** по всем 9 шагам (mean + max %)
- *bottom-left* — Средняя задержка итерации (мс) для пайплайнов A / B / C / C+лимиты
- *bottom-center* — Вклад компонентов в задержку: baseline → +HI decode → +YOLO
- *bottom-right* — **Сравнение лимитов**: CPU и fps Pipeline C без и с ограничением

**Измеренные результаты (CAM_01_9_D, 60s, `--yolo-warmup 20 --yolo-iters 100 --yolo-max-fps 0.33 --hi-decode-max-fps 1.0 --step-pause-s 15`)**

Производительность существенно зависит от температуры CPU и фоновой нагрузки.  
Разброс между прогонами — до **2.2×** по YOLO latency:

| Компонент | Холодный / малая нагрузка | Тёплый / фоновая нагрузка | С паузами между шагами |
|-----------|--------------------------|--------------------------|----------------------|
| LOW raw | 12.85 fps | 12.85 fps | 12.82 fps |
| HI raw | 12.85 fps | 12.85 fps | 12.80 fps |
| HI plausible | 2.55 fps | 2.42 fps | 2.31 fps |
| YOLO 640×720 | 378ms / 542ms p95 | 843ms / 968ms p95 | **656ms / 769ms p95** |
| YOLO 2304×2592 | 412ms / 632ms p95 | 906ms / 1003ms p95 | **1362ms / 1751ms p95** |
| Pipeline A loop | 77.8ms | 81.4ms | 108ms |
| Pipeline B loop | 298.9ms | 607.6ms | 1387ms |
| Pipeline C loop (без лимитов) | 956.2ms | 1826.3ms | **2945ms** |
| **Pipeline C+лимиты** | — | — | **629ms (4.7× лучше C)** |
| yolo_skipped (C+лимиты) | 0 (cooldown 1s) | 0 (cooldown 1s) | **16 из 33** ✅ |
| hi_decode_skipped (C+лимиты) | — | — | **65 из 82** ✅ |
| CPU Pipeline C / C+лимиты | — | — | 96% / **92%** |

> **Лимиты работают.** Pipeline C+лимиты (HI≤1fps, YOLO≤0.33fps): **1.59fps loop vs 0.34fps без лимитов = 4.7× быстрее**. Cooldown 3s (0.33fps) виден в бенчмарке: 16 пропусков из 33. При cooldown 1s пропусков не было (loop=1826ms >> 1.0s cooldown).

> **Узкое место — HI plausible: 2.3–2.6 fps вместо 12.85fps.** `frame_decode_plausible` на кадре 2304×2592 блокирует loop на 300-400ms. Лимит `--hi-decode-max-fps 1.0` снижает нагрузку: 65 из 82 декодирований пропущено. В production HI проходит через `StreamReader` (фоновый поток) с тем же `decode_max_fps`.

> **YOLO на HI медленнее LOW в 2×** (1362ms vs 656ms при одинаковом входе 640×640). Причина — resize 2304×2592 → 640×640 на загруженном CPU (6 Мп → 14× сжатие). Реальная production-латентность YOLO — **1.4–1.8s**, что соответствует рекомендуемому лимиту `--yolo-max-fps 0.33` (раз в 3 сек).

> **Тепловой троттлинг**: паузы между шагами улучшили YOLO LOW (656ms vs 843ms), но YOLO HI вырос (1362ms vs 906ms) — система была нагружена фоновыми процессами (~70-80% CPU база). Pipeline A деградировал до 108ms (vs 81ms) по той же причине.

### Ограничение частоты (`5_diff_yolo_boxes_low.py`)

#### `--yolo-max-fps`

YOLO выполняется синхронно в основном потоке (~400–1100 мс под нагрузкой). Без ограничения возможен каскад: после YOLO накопленный diff в буфере сразу триггерит следующий YOLO.

```
python scripts/cameras/5_diff_yolo_boxes_low.py --yolo-max-fps 0.33
```

- Если `diff > threshold`, но с предыдущего YOLO прошло меньше `1/fps` сек — **пропускаем YOLO, но обновляем `prev_gray`**.
- Пока пауза активна, `cap.read()` вычитывает буфер; к её концу буфер пуст и `prev_gray` актуален.
- После паузы первый же крупный diff корректно триггерит YOLO на свежем кадре.

| Сценарий | Рекомендуемый лимит |
|----------|-------------------|
| Надёжная гарантия (YOLO p95 под нагрузкой = 1.6s) | `--yolo-max-fps 0.33` *(≈раз в 3с, рекомендуется)* |
| Баланс (YOLO mean под нагрузкой = 1.1s) | `--yolo-max-fps 0.5` *(раз в 2с)* |
| Холодный CPU / малая нагрузка (YOLO mean ~380ms) | `--yolo-max-fps 1.0` *(раз в 1с)* |
| Выключено (без ограничений) | `--yolo-max-fps 0` |

Значение сохраняется в `run_params.json` каждого прогона.

Эффект лимита виден в `1_fps_bench.py` как шаг **[9/9] Pipeline C+лимиты** — сравнивается с шагом [8/9] без ограничений.

### `2_compare_lohi.py` — Сравнение LOW vs HI детекции

```
python scripts/bench/2_compare_lohi.py --pairs 20
python scripts/bench/2_compare_lohi.py --pairs 50 --threshold 0   # все кадры, не только с движением
```

**Что делает:** захватывает N пар кадров (LOW + HI почти одновременно), запускает YOLO на каждом, сохраняет аннотированные изображения и CSV.

**Логика захвата пары:**
1. Читает LOW кадры в цикле, считает motion diff (`mean_abs_diff`)
2. Когда `diff > threshold` (движение обнаружено) — фиксирует пару: текущий LOW + последний кадр из `StreamReader` HI
3. Если HI-кадр старше 3 сек — пара пропускается
4. Запускает YOLO на обоих кадрах (без motion-гейтинга, всегда)

**Вывод (`.output/bench/2_compare_lohi/run_*/`):**

```
pair_NNN_low.jpg    — кадр LOW с bounding boxes
pair_NNN_hi.jpg     — кадр HI с bounding boxes  
pair_NNN_side.jpg   — side-by-side (одна высота, подписи с разрешением и числом детекций)
results.csv         — все пары в одном файле
```

**Колонки CSV:**

| Колонка | Значение |
|---------|---------|
| `diff` | motion diff в момент захвата |
| `hi_age_s` | свежесть HI-кадра (сек) — показывает рассинхрон потоков |
| `low_w/h`, `hi_w/h` | разрешения кадров |
| `low_dets` / `hi_dets` | число детектированных людей |
| `low_max_conf` / `hi_max_conf` | максимальный confidence детекции |
| `agree` | `yes` если оба потока согласны (оба нашли / оба не нашли) |

**Итоговая сводка в stdout:**
```
=== Итог (20 пар) ===
  Совпадение LOW/HI: 18/20 (90%)
  LOW детектировал: 12/20
  HI  детектировал: 14/20
```

**Типичное использование:** проверить что HI даёт ≥ LOW по числу детекций, и что `agree` ≥ 85%. Если HI часто пропускает — проверить `hi_age_s` (HI может отставать на 2–4 сек при перезапуске StreamReader).

**Ключевые параметры:**

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `--pairs` | 20 | Количество пар для захвата |
| `--threshold` | 6.0 | Порог diff для захвата (0 = захватывать каждый кадр) |
| `--conf` | 0.35 | YOLO confidence threshold |
| `--hi-scale` | 0.5 | Масштаб HI-кадра перед YOLO (0.5 = 1152×648) |

## Ночной прогон 5_1 — выводы по поведению дифов

**Прогон:** `5_1_diff_yolo_boxes_low / run_20260628_003445_msk`  
**Длительность:** ~8 часов, 00:34–08:30 МСК  
**Камеры:** CAM_01_9_D (нижняя половина кадра) и CAM_01_9_U (верхняя половина)  
**Порог:** 3.3  
**Итого кадров diff:** 717 432, **событий (saves):** 427  

### Двуполосная структура дифов

Обе камеры имеют **два устойчивых пояса** в распределении diff (хорошо видно на скаттер-плоте):

**Первая линия — вблизи нуля** (фоновый шум):
- Обе камеры, схожий уровень
- Ночью: до ~0.5; утром: до ~1.2

**Вторая линия — верхний кластер** (~2–3):
- Вероятная природа: сцена содержит постоянный источник diff (движение листвы/теней, изменение освещения, rate-control артефакты кодека при сложной текстуре)
- Разная по камере и по времени суток:

| Камера | Вторая линия (ночь) | Вторая линия (утро) | Превышение порога 3.3 |
|--------|--------------------|--------------------|----------------------|
| CAM_01_9_D (orange) | ~2.0 | ~2.2 | **никогда** |
| CAM_01_9_U (blue) | ~2.5 | ~3.0–3.5 | **да, утром** |

**Почему D никогда не триггерит:** вторая линия D стабильна на ~2.0–2.2. До порога 3.3 остаётся запас ~1.1.

**Почему U триггерит утром:** вторая линия U начинается с ~2.5 ночью и к утру вырастает до ~3.0–3.5 — пересекая порог 3.3. Именно это генерирует 427 событий после 06:30.

**Следствие для настройки:** порог 3.3 работает для U, но не позволяет детектировать события на D вообще. Для D потребовался бы отдельный per-camera порог ~2.5–2.8 (чуть выше её верхней линии ~2.2).

### Временна́я структура событий

- **00:34–06:30** (6 часов): нулевая активность на U. Только регулярный heartbeat (~каждые 10 мин) на обеих камерах.
- **06:30–08:30** (2 часа): 427 diff-событий на U (все сохранения — `diff/U`). Активность нарастает к 07:30–08:30.
- D-камера за всё время не дала ни одного diff-события.

> **⚠️ Оговорка (не путать «нет diff-событий» с «не было людей»).** «Нулевая активность»
> и «0 событий» здесь = **diff не пересёк порог 3.3**, а НЕ «людей не было». Два независимых
> подтверждения, почему это разные вещи:
> 1. Регулярный **heartbeat каждые ~10 мин** доказывает, что камера всё это время **работала**
>    (heartbeat пишется независимо от движения). «Тихо ночью» ≠ «камера офлайн».
> 2. На **D порог 3.3 не срабатывает НИКОГДА** (её верхняя линия ~2.2 < 3.3) — значит «0 событий
>    на D» = «порог для D завышен», а не «в нижней зоне никого не было». Человек в кадре даёт
>    diff ~4–10, но если он в дальней/верхней части D или движется медленно, diff может не дойти
>    до 3.3.
>
> Практический критерий «людей ночью действительно не было» — считать по **diff-кадрам с
> адекватным per-зонным порогом**, а не по факту «мало сохранений». С 1.23.0 порог настраивается
> по зоне (`<VAR>_MOTION_THRESHOLD`) — рекомендация ниже (D ~2.5–2.8) теперь выполнима.

### Интервал кадров

Средний интервал ~80 мс (12.5 fps) — стабильно всю ночь. После ~07:00 появляются спорадические спайки до 200–1200 мс — следствие CPU-нагрузки от YOLO при росте числа событий.

### Артефакт «белый/чёрный кадр» — всплески diff до 60

Наблюдались в других прогонах (не только ночном). Камера на короткое время выдаёт кадр, целиком залитый белым или чёрным — либо с большой белой/чёрной областью. Характеристики:

- diff в момент артефакта: **до 60** (на порядок выше нормальной активности)
- Причина: аппаратный сбой камеры или потеря потока с неправильным recover-кадром
- **Не фильтруется порогом** — любой разумный порог для детекции людей пропустит эти всплески

**Почему это не проблема для пайплайна:** YOLO не находит людей в белом/чёрном кадре → детекция не срабатывает → кроп не создаётся. Артефакт проходит через diff-детекцию, но отфильтровывается на уровне YOLO.

### Диапазоны diff: справочные значения

| Источник | Типичный diff |
|----------|--------------|
| Фоновый шум (первая линия) | 0–1.2 |
| Вторая линия (сцена, кодек) | 2.0–3.5 |
| Человек в кадре | **~4–10** |
| Артефакт «белый/чёрный кадр» | **до 60** |

Пороговое значение 3.3 отсекает фоновый шум и большую часть второй линии, при этом захватывая людей (от ~4). Артефакты с diff 60 проходят через порог, но отсеиваются YOLO.

### Выводы для настройки

1. **Порог 3.3 корректен для U**: хорошо отделяет ночной фон от утренней активности.
2. **D-камера при пороге 3.3 никогда не триггерит** — если нужна детекция в нижней зоне, нужен отдельный per-camera порог ~2.5–2.8.
3. **Разные камеры → разные пороги**: верхняя линия D (~2.2) и U (~2.5–3.5) существенно отличаются.
4. **Утренняя активность** начинается резко в 06:30 — можно использовать для расписания прогонов.
